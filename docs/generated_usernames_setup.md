# Автоматические username

## Развёртывание

Из корня приложения выполните `npx supabase db push` для связанного проекта.
Миграции: `202610110001_harden_generated_usernames.sql` и
`202610110002_pin_username_formatter_search_path.sql`.
Если первая уже применена, команда применит только вторую.
Они не меняют существующие username, таблицы, индексы, счётчик или Flutter-клиент.
Удалённая БД при разработке не изменялась.

## Поведение

- Формат прежний: `u` и семь цифр/букв base36.
- Свободный очередной ник: одна проверка по уникальному индексу.
- Занятый очередной ник: проверка пакетов по 128 кандидатов без полной
  загрузки/сканирования профилей. Выбирается первый свободный билет пакета.
- Пакет резервируется через `nextval`; неиспользованные билеты становятся
  пропусками. Последовательность не перематывается, поэтому одновременные
  регистрации не получают один и тот же автоматический билет.
- На одну выдачу: один исходный кандидат и максимум 512 пакетов
  (65 537 кандидатов). При полностью занятом диапазоне возвращается
  `username_allocation_busy` / SQLSTATE `54000`. Следующая попытка продолжает
  за уже пройденным диапазоном; бесконечного цикла нет.
- Конкурентный конфликт уникальности username при вставке профиля повторяется
  до восьми попыток внутри существующей серверной операции. Проверяются схема,
  таблица и имя уникального индекса; другие ошибки не маскируются.
- Ручная смена занятого ника по-прежнему получает ошибку «ник занят».
- Bootstrap существующего профиля использует его текущий ник, не генерирует
  новый и сохраняет прежние правила имени, даты рождения, аватара и согласий.
- Нет новых RPC клиента, соединений, фоновых таймеров или подписок.

Числовой форматтер — приватная SQL-функция с SQL-standard `RETURN`-телом:
функции и операторы разрешаются при создании, а не через search_path вызывающего.
Она не доступна `anon`/`authenticated` и не является SECURITY DEFINER.
Дополнительно закреплён пустой `search_path`, что устраняет предупреждение
`Function Search Path Mutable`. Пакетный генератор вычисляет base36 непосредственно
в SQL-выражении: закрепление пути форматтера не добавляет отдельного вызова
функции на каждый кандидат. Тесты сверяют оба варианта с исходным алгоритмом
на границах разрядов. Bootstrap остаётся SECURITY INVOKER.

## Локальная проверка

Запускайте только на локальной Supabase после применения миграции:

```powershell
Get-Content -Raw supabase/tests/generated_usernames.sql |
  docker exec -i supabase_db_Yap_chat psql -U postgres -d postgres -X -v ON_ERROR_STOP=1
node supabase/tests/generated_usernames_concurrency.mjs
Get-Content -Raw supabase/benchmarks/generated_usernames.sql |
  docker exec -i supabase_db_Yap_chat psql -U postgres -d postgres -X -v ON_ERROR_STOP=1
```

SQL-тест и benchmark используют временные счётчики и откатывают фикстуры.
Concurrency-тест создаёт случайные тестовые UUID и удаляет только эти аккаунты
в `finally`; он расходует несколько обычных билетов рабочего локального счётчика,
но никогда не сбрасывает его. Одновременный запуск нескольких экземпляров этого
теста либо регистрации вне теста может нарушить его управляемый сценарий гонки.

Проверены: закреплённый search_path и права форматтера, формат/границы диапазона,
переходы всех разрядов base36, 1000 занятых ников, свободная дырка,
bootstrap существующего и отсутствующего профиля, реальные гонки с ручной
сменой, 16 параллельных регистраций, ручной дубликат, оба предела повторов,
нерелевантные unique-ошибки и отсутствие частичного аккаунта после ошибки.

Замер локально на PostgreSQL 17.6, 100 000 других профилей, 20 повторений
после прогрева (медиана времени только внутри БД, не сетевой задержки):

| Подряд занято | Старый генератор | Новый генератор |
| --- | ---: | ---: |
| 0 | 0,006 мс | 0,005 мс |
| 100 | 0,494 мс | 0,315 мс |
| 1000 | 5,749 мс | 2,675 мс |
| 10 000 | 60,748 мс | 27,118 мс |

Это результат конкретного локального прогона, а не SLA для удалённой Supabase.
Замер сделан после применения обеих миграций; проверка результата не входит
во время самой выдачи username.
План пакетного запроса отдельно проверен через `EXPLAIN ANALYZE`: используется
индекс по `lower(username)`, полного сканирования профилей нет.
